# 候補を変換箇所で分ける選択方法の検証（2026-09-09）

32候補から10候補を選ぶ際、先頭3件を維持し、残りを先頭表記との差分区間でグループ化して巡回選択する方法を検証した。この方法は不採用。正解候補を含む入力は1,420→1,394となり、追加で拾えた11件に対して37件を失った。

| 集合 | 問題数 | 同じ集合の先頭10件 | 差分区間で選ぶ10件 | 32件すべて |
| --- | ---: | ---: | ---: | ---: |
| JWTD | 400 | 286 | 274 | 325 |
| AJIMEE | 200 | 171 | 165 | 179 |
| UD dev | 331 | 327 | 327 | 330 |
| UD test | 323 | 320 | 320 | 323 |
| 追加JWTD | 200 | 144 | 137 | 168 |
| 中程度JWTD | 200 | 172 | 171 | 185 |

数値は候補に期待表記が存在する件数であり、第一候補の正解数ではない。比較は同じ32候補リクエストの中で行っており、現行10候補の生成から得た結果そのものではない。ランキングリクエストを作れない入力は空の候補集合として扱う。

差分区間は共通の接頭・接尾文字を除いた、先頭候補上の文字範囲で定義した。期待出力は選択処理に使わず、実装してから全1,654問で照合した。候補の変わる箇所を増やすだけでは、有用な同音語や表記候補を捨ててしまう。さらに、この方式でも32候補を生成する費用は残るため、候補数を10へ戻しただけで現行と同じ速度になるわけではない。

再現資料は `target/evaluation/candidate-diversity-20260909/`。現在のconverterを使う実験用coreから実際の明示変換ランキングリクエストを抽出した。`*-requests.json`、`analyze.py`、`comparison.json` に全候補と選択・集計を保存。製品ソースは実験用プローブのビルド後に復元済みで、QAアプリに変更はない。
