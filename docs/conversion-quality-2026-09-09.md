# 2026-09-09 変換品質の改善

これは前段の候補回収改善の記録。続く変更と最新の検証は
[LIVE変換の長文表示安定性](live-stability-2026-09-09.md)に記録している。

作業開始時の未コミット変更を含む状態と比較した。今回の変更は候補一覧の探索と数詞の解釈、
その回帰テストに限定している。既存の辞書やモデルの追加学習、単語別のコスト調整は行っていない。

## 変更

- 同じ読み境界・表記・右品詞へ合流する経路について、接頭辞の表記が一致していれば
  分割が違っても最小コストの経路だけを候補探索に残す。異なる右品詞は保持する。
  32-bitの逐次ハッシュで文字列比較の前に絞り、ハッシュが一致した場合も実際のUTF-8列を
  照合する。探索幅、最大状態数、64-byteのN-best nodeは維持し、文字列の追加割当ても行わない。
- この整理は候補一覧の生成に適用する。停止後のworkerが取得する候補一覧も対象になる。
  `convert_n_best`を使う同期LIVEの確信度判定は
  従来の探索方針を維持する。候補の増加で既存の確信度marginが変わることを避ける。
- 数詞の大単位を降順に限定し、乗算・加算のオーバーフローを検査する。明示的なゼロを
  省略された一と同一視しない。大きな数値の漢字・混合表記では京を兆と誤表示しない。
  新しい単位読みの追加は含めない。

## 通常変換

同一の辞書・文脈・N-best幅10で比較。数値は正解件数であり、モデルを使わない候補一覧の評価である。

| 集合 | 件数 | 第1候補 修正前→後 | 上位10候補 修正前→後 |
| --- | ---: | ---: | ---: |
| JWTD train由来の固定dev | 400 | 117→117 | 269→285 |
| UD Japanese GSD dev | 331 | 269→269 | 328→328 |
| UD Japanese GSD test | 323 | 266→266 | 321→321 |
| AJIMEE | 200 | 106→107 | 167→171 |

4集合で第1候補の正解からの退行0件。上位10候補はJWTDで17件回収・1件消失、
AJIMEEで4件回収・消失0件、UDでは不変だった。
JWTDで外れた1件は「うち明ける」を唯一の許容表記とする項目で、第1候補の「打ち明ける」は
変更前後とも同じ。表記違いであっても、評価上の消失1件として数えている。
JWTDの第1候補は表記・コストとも全件不変。JWTDの許容解は1変種だけなので、絶対値を
一般的なIME品質と同一視しない。今回の既存評価集合は失敗の検出にも参照しており、
未知の実入力や他製品に対する優位性を証明する評価ではない。

追加の固定dev 4,788件では、接頭辞の分割が同じ場合だけまとめる試作の上位10候補包含率
`0.712406`から、分割をまたいで比較する方式の`0.727652`へ改善した。82件回収・9件消失で、
第1候補の改善・退行はともに0件。ハッシュを加えた後も、この4,788件の候補表記とコストは
ハッシュなし版と全件一致した。

## 入力途中の表示

かなを1文字ずつ入力する同期Core評価では、4集合とも最終精度、数字混入、かな戻り件数、
固定可能な文節の差し替え件数を維持した。JWTDとUD dev/testは全遷移品質指標が一致した。

AJIMEEでは1件だけ、rewriteが1455→1461回、3595→3755文字、rollbackが1215→1221回、
2834→2994文字となった。ゼロに続く千を誤って1000とする経路を除去した結果、従来は
かなのままだった長文の一部が途中で変換され、再びかなへ戻る。通常変換の正解は回収できたが、
この同期表示の切り替わりは残る制約である。

探索方針をLIVEにも一律適用する案は、既存のLIVE回帰テストを破ったため採用していない。
兆・京の読みを数詞生成へ追加する案も、一般語に数字を混ぜる誤変換を増やしたため取り下げた。

## 同梱モデルを使う変換

macOSビルド内のモデルとSHA-256が一致する `zenz-v3.2-small-Q3_K_M-requant-fixed.gguf`
を、製品のFFI task生成・実行・適用経路へ接続した。個人辞書や学習履歴は読み込まず、モデルや
重みを変更せずに比較した。

| 集合 | 入力停止後の正解数 修正前→後 | モデル付きSpace正解数 修正前→後 |
| --- | ---: | ---: |
| JWTD 400件 | 196→198 | 150→150 |
| UD dev 331件 | 277→277 | 279→279 |
| UD test 323件 | 276→276 | 271→271 |
| AJIMEE 200件 | 146→146 | 123→124 |

4集合とも、最終版でCoreが正解した入力をニューラル処理が不正解へ変えた件数は0。
これは停止後taskの評価であり、インストール済みIMEの実画面を操作した検証ではない。

## 速度とメモリ

Apple M3、Rust 1.98.0、同一Release profileで、ビルドやモデル評価が終わった後に
変更前後を交互に3回実行した。表は各runのp95の中央値で、モデル推論を含まない。

| 集合 | 候補生成p95 修正前→後 |
| --- | ---: |
| JWTD | 7.75→9.83 ms |
| UD dev | 0.56→0.60 ms |
| UD test | 0.48→0.55 ms |
| AJIMEE | 10.73→13.61 ms |

長文の候補生成時間は約27%増える。p95は20 ms以内だが、AJIMEEのmax中央値は
17.09→21.57 msであり、全入力20 ms以内を保証するものではない。

1項目だけ評価する新規プロセスを3回起動した中央値は、起動・データ読込・評価を合わせて
10.84→11.66 ms、最大RSSは7,258,112→7,340,032 bytesだった。ファイルキャッシュは排除しておらず、
IMEアプリ全体の冷起動を測った値ではない。

接頭辞を直接たどる最初の試作はAJIMEE p95を約31 msまで悪化させた。ハッシュ一致の確認を
文字列比較より前へ移すことで上記の時間へ抑えた。照合結果の固定キャッシュは、ハッシュのみの
版より遅くなったため不採用とし、最終版にはキャッシュ用の追加割当てを残していない。

## 再現用の記録

ローカルの `target/evaluation/overnight-20260909/` に開始時のソース、比較用Releaseバイナリ、
SHA-256、各集合のN-best全件、同期LIVE遷移、集計 `summary.json` を保存している。
`*-accepted*` が最終採用版で、`*-final*` は途中の比較用試作である。
`implementation.patch` は開始時の混在した作業ツリーに対する今回の3ファイルの差分だけを含む。
通常変換は同梱の `slime-evaluate ajimee --input ... --export-nbest ... --json`、
同期LIVEは `slime-live-transition-evaluate --input ... --json` を使用した。

最終版はRust workspaceの全447テストが通過し、2件は既存のignore指定。
候補回収を初回Spaceから確認するCore回帰と、C APIから同じ候補を取得する回帰も通過した。
C ABI smoke testは実際のRelease共有ライブラリをリンクして実行した。
`scripts/test-macos-adapter.sh` によるSwiftアダプター試験も通過した。

標準Clippyは今回未変更の `dictionary_packs.rs:601` に対する新しい
`chunks_exact_to_as_chunks` lintで停止した。ビルド時にはローカルRust toolchainの
`rust-objcopy`が `libLLVM.dylib` を見つけられないwarningも出るが、Releaseビルドと
C ABI実行は成功している。
既知のlintだけを `-A clippy::chunks_exact_to_as_chunks` で除いた
workspace全targetの `-D warnings` は通過した。

インストール済みIMEの差し替え、配布パッケージの公開、他IMEとの比較はまだ行っていない。
