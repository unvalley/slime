# 明示変換の候補数拡大実験（2026-09-09）

候補保持の効率化後、明示変換の通常候補生成とニューラル評価対象を10から32へ広げる実験を行った。計1,654問で完全一致1048→1052、改善7・悪化3。悪化に意味の異なる語の選択が含まれるため、この設定はまだ採用しない。

| 集合 | 問題数 | 現行 | 32候補 | 改善 | 悪化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| JWTD | 400 | 180 | 184 | 4 | 0 |
| UD dev | 331 | 279 | 279 | 0 | 0 |
| UD test | 323 | 271 | 271 | 0 | 0 |
| AJIMEE | 200 | 139 | 138 | 0 | 1 |
| 追加JWTD | 200 | 77 | 78 | 3 | 2 |
| 中程度JWTD | 200 | 102 | 102 | 0 | 0 |

改善には「復讐渡渉して→復讐と称して」「熱戦銃→熱線銃」「敗れて配送し→敗れて敗走し」「地理先行卒業→地理専攻卒業」がある。一方、「ボールを奪取→ダッシュ」「ネジで変身→返信」「一旦→いったん」の3問が完全一致から外れた。最後は表記差だが、最初の2問は意味に関わる悪化。

候補数以外の設定は維持した。明示変換の重みは20文字以上0.45、その他0.2。LIVEの候補上限は変更せず、全6集合でLIVE変更記録・worker status集計が現行と一致した。

最初の実験差分は同名メソッドの取り違えでLIVE側も変更していたため中止し、`rejected-mixed/` に隔離した。上記結果は明示変換に限定した差分を確認してから再ビルド・再実行したもの。製品ソースは実験バイナリ作成後に変更前とバイト一致で復元し、通常のreleaseバイナリも再ビルドした。QAアプリは変更していない。

再現資料は `target/evaluation/explicit-width-20260909/`。`experiment.patch`、`core-experiment.rs`、`evaluator-width32`、`run.py`、`analyze.py`、`comparison.json`、全集合の `*-neural.json` を保存した。初期の評価と復元ビルドが重なったため、この実行の時間は性能比較に使わない。

次は悪化例について、新たな候補が不適切な順位を得たのか、候補集合の変更によるモデル採点の変化が関与したのかを切り分ける。単に悪化例を除外する長さの閾値や例文の特例は加えない。

## 悪化3例の再採点による原因確認

実際の `candidate_ranking_request` を10候補版・32候補版から取得し、同じモデルで再採点した。資料は `target/evaluation/explicit-width-scores-20260909/` の `*-request.json`、`*-scores.txt`、`*-status.json`、`summary.json`。

- AJIMEE1429の「奪取→ダッシュ」: 10候補では採点成功し「奪取」が首位。32候補では `candidate batch exceeds the unshared token limit` で失敗した。FFIは採点エラー時に再順位付けを行わず、辞書先頭の「ダッシュ」が残る。この例はモデルが誤った候補を高く評価したものではない。
- 追加JWTD300950の「変身→返信」: 両候補数で採点成功。共通候補のloglikは出力精度で差0。新しく加わった「返信すると髪が極端に逆立」が高評価を得た。モデルによる候補選択の問題。
- 追加JWTD107220の「一旦→いったん」: 両候補数で採点成功。共通候補のloglikは出力精度で差0。新規のひらがな表記が上位になった。完全一致上の表記差。

スコア比較はデバッグ出力の小数6桁精度。bitwise同一を主張するものではない。失敗した採点もエラーとして保存し、空のスコアを正常な結果として扱わない。

`score_requests` は候補を固定件数ごとに分割しているが、分割内のトークン総数が上限を超える場合はエラーになる。候補数拡大の前提として、件数だけでなくトークン容量に収まるように分割する処理を検討する。単一候補そのものが容量を超える場合のエラー境界は維持する必要がある。

トークン容量に応じた分割を採用した現在ソースで、同じ明示変換32候補の実験を再ビルド・再実行した。計1,654問で完全一致1048→1055、改善9・悪化2となった。

| 集合 | 現行10候補 | 実験32候補 | 改善 | 悪化 |
| --- | ---: | ---: | ---: | ---: |
| JWTD | 180 | 184 | 4 | 0 |
| UD dev | 279 | 279 | 0 | 0 |
| UD test | 271 | 271 | 0 | 0 |
| AJIMEE | 139 | 141 | 2 | 0 |
| 追加JWTD | 77 | 78 | 3 | 2 |
| 中程度JWTD | 102 | 102 | 0 | 0 |

AJIMEE1429の「奪取→ダッシュ」という悪化がなくなり、追加で「水平安定版→水平安定板」「得意な近代の権力→特異な近代の権力」が完全一致に改善した。残る悪化は追加JWTDの「変身→返信」と「一旦→いったん」。LIVE変更記録・worker status集計は全6集合で現行と一致した。

資料は `target/evaluation/width-token-20260909/` の評価バイナリ、`run.py`、`analyze.py`、全評価JSON、`comparison.json`。製品ソースは実験後に復元し、通常releaseも再ビルドした。QAアプリの候補数は10のまま。純改善は確認できたが、採用判断には応答時間と残る悪化の評価が必要。ゼロ悪化を機械的に要求するのではなく、精度と操作時の負担の両方を確認する。

## Space変換時間の比較と32候補の判断

入力長1〜9・10〜19・20〜39・40文字以上から各15問、計60問を固定seedのSHA-256順で抽出した。同一の60問を現行版と32候補版で交互に3組実行した。各版の出力・LIVE記録・statusは3反復で一致した。

| 指標（各反復の中央値） | 現行10候補 | 実験32候補 |
| --- | ---: | ---: |
| Space p50 | 35.61ms | 71.45ms |
| Space p95 | 126.74ms | 248.31ms |
| Space 最大 | 170.97ms | 365.80ms |

この60問の完全一致は38→39。計測は評価器のSpaceイベント処理を囲み、実機の物理キー入力や画面反映時間ではない。長さごと同数の抽出なので、日常利用の入力頻度分布を再現したものでもない。

一律32候補は通常の応答時間をほぼ倍にするため採用しない。次はモデルの並列候補数に合わせた16候補を別途評価する。資料は `target/evaluation/width-latency-20260909/` の `manifest.json`、入力、各実行JSON、`run.py`、`analyze.py`、`comparison.json`。

## 16候補の精度・応答時間

同じ明示変換箇所だけを16候補へ広げ、1,654問を再評価した。完全一致1048→1049、改善2・悪化1。改善は「高圧光熱→高圧高熱」「得意な近代の権力→特異な近代の権力」。悪化は「一旦→いったん」という表記差だった。LIVE記録・worker status集計は全集合で一致した。

32候補と同じ60問を使い、現行10候補との交互3組計測を実施した。

| 指標（各反復の中央値） | 現行10候補 | 実験16候補 |
| --- | ---: | ---: |
| Space p50 | 35.49ms | 40.76ms |
| Space p95 | 128.66ms | 151.79ms |
| Space 最大 | 171.88ms | 213.14ms |

各版の出力は3反復で一致。60問の完全一致は38→39。計測範囲と長さ別抽出の限界は32候補の計測と同じ。

16候補の費用増は32候補より小さいが、全件に広い探索を行う割に精度の変化は限定的なため、現時点では一律採用しない。次の検討は単なる件数増加ではなく、限られた評価枠へ候補を選ぶ処理。製品ソースは復元済み、QAアプリの候補数は10を維持。

資料は `target/evaluation/width16-20260909/`（全件精度、差分、実験バイナリ）と `target/evaluation/width16-latency-20260909/`（60問、全反復結果、選択条件、分析スクリプト）。

その後、文脈ルールが空の場合の探索省略を導入し、別の長文200問も検証した上で、20文字以上だけ16候補とする設定を採用した。現在の結果と遅延の条件は [長文の明示変換候補](long-explicit-width-2026-09-09.md) を参照。一律の拡大は引き続き採用していない。
