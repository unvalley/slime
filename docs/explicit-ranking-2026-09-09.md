# 長い読みのSpace変換 — 2026-09-09

後続の[モデル候補の共通部分共有](neural-prefix-performance-2026-09-09.md)で、出力を維持した速度改善を記録している。

## 採用した変更

20文字以上の読みを明示的にSpace変換するときだけ、モデル重みを0.2から0.4にする。
短い読みと自動LIVE変換の設定は変えない。[一律の重み変更](ranking-investigation-2026-09-09.md)で
短い入力とLIVEが悪化したため、全文を明示的に変換する場面を分けた。

既存C APIの重み指定は維持し、新しい任意設定APIを追加した。モデルを読み込んだ後に設定でき、
最小文字数0で解除、モデルの再読み込みでリセットする。文字数はUTF-8バイト数ではなくUnicode文字数。
macOSビルドでは同梱モデルがある場合に20文字・0.4を設定する。Swiftの呼び出し元が重みを
明示指定した場合は、その指定を優先する。

設定は `SLIME_NEURAL_EXPLICIT_LONG_LAMBDA` と `SLIME_NEURAL_EXPLICIT_MINIMUM_CHARACTERS`。
後者を0にすると無効化できる。モデルそのもの、候補探索の幅、LIVEの重みや採用マージンは変更していない。

## 品質

| 評価集合 | Space正解数 前 → 後 | 改善 / 悪化 | LIVE正解数 |
| --- | ---: | ---: | ---: |
| JWTD 400件 | 150 → 178 | 29 / 1 | 198のまま |
| UD dev 331件 | 279 → 279 | 0 / 0 | 277のまま |
| UD test 323件 | 271 → 271 | 0 / 0 | 276のまま |
| AJIMEE 200件 | 124 → 138 | 14 / 0 | 147のまま |

例：「都市部に構想団地が着工される」→「都市部に高層団地が着工される」。
JWTDで失った1件は「遥かに」が「はるかに」になる表記差で、完全一致評価の悪化として数えた。
合計43件を改善し、1件を失った。全項目が改善したという主張ではない。

20文字の仮説を固定して検証した。UDの両集合は9文字以下の入力なので、中長文の一般化を
証明するものではない。これらは繰り返し使用している評価集合であり、新しい独立評価も今後必要。

全項目のSpace結果を出すよう評価ツールを拡張した。従来のLIVE失敗例一覧だけでは、LIVEが
正しかった項目のSpaceでの悪化が見えないためである。全項目を照合し、実際のC APIの出力が
事前に固定した条件による選択と一致すること、LIVEの全変更記録が前後で一致することを確認した。
個人辞書・入力履歴は使っていない。

## Space処理時間

JWTD・AJIMEE・UD devから等間隔に各20項目、計60項目を取り、ビルド・他のモデル実行終了後に
設定の有無を交互に3回比較した。同一最終実行物でのC APIのSpace処理時間で、画面描画は含まない。
各回のパーセンタイルの中央値はp50が34.89 → 35.08ms、p95が176.66 → 176.22ms、
最大値が230.09 → 231.69ms。追加設定による大きな遅延増加は見られないが、高速化を示す結果ではない。
モデルの長文処理には依然として約0.2秒かかるケースがあり、今後の改善対象として残る。

`target/evaluation/explicit-ranking-20260909/`にソースの開始時コピー、評価JSON、比較スクリプト、
仮説、ログを保存。`accepted-summary.json`がC API経由の結果、`policy-analysis.json`が項目別比較。

さらに同じSwiftコード・アプリ設定・同梱ライブラリを使う検証アプリで、上記「高層団地」の
改善と、呼び出し元による0.2の明示指定の維持を確認した。

最終アプリはモデル読み込み成功まで検証し、署名も検査した。
