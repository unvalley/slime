# IME機能調査とSlimeの優先課題

- 調査日: 2026-08-07
- 対象: 一般的な商用IMEの機能群、Slime `main` + 現在の作業ツリー
- 判断軸: 変換品質、ローカル完結、軽量性、入力中の安全性、テスト可能性

## 結論

機能数を追いかけるのではなく、Slimeでは次の順で取り込む。

1. 文脈を使った候補順位と、候補集合に正解を残すこと
2. 一時的な入力で普段の表記を壊さない学習
3. 読みを勝手に壊さない、説明可能で保守的な入力ミス訂正
4. ローカル履歴による省入力と、誤学習を自分で管理できるUI
5. macOS/Windowsの実アプリで候補選択まで通る配布品質

生成AI、クラウド辞書、文章校正、辞典、連絡先・カレンダー連携は高機能IMEで提供されることがあるが、Slimeの「軽量・ローカル完結・入力内容を外部へ送らない」という価値を弱める。少なくとも上記5項目より先には実装しない。

## 一般的なIME機能とSlimeへの判断

| 機能群 | 利用者にとっての目的 | Slimeの現状 | 判断 |
| --- | --- | --- | --- |
| 文脈変換 | 単語のつながりから自然な変換結果を提示 | 同じ前後ペアを2回確定した端末内履歴は通常候補の順位に使う。初回入力の汎用的な文脈モデルは未実装 | P0。ローカル適応は実装、cold start品質は継続 |
| 変換強度の学習 | 一度だけ使った表記より普段の表記を優先 | 5回以上の定着層を単発選択より優先する。5文字以上の明示訂正は同じengine内の次回LIVEへ即時反映し、再起動後は2回選択gateを維持 | P0。定着/一時/session即時反映を実装、実アプリ検証を継続 |
| 推測変換 | 数文字から長い候補、確定直後の候補を提示 | 5回以上使ったローカル履歴と、再起動後も残る端末内文脈による補完のみ | P1。ローカルのまま段階的に拡張 |
| 入力ミス訂正 | ローマ字・かな入力特有のミスを自動修復し、ガイダンスを表示 | 保守的なローマ字訂正候補を実装。元入力を先頭に残して訂正後の読みを表示 | P1。誤訂正評価を拡充 |
| 誤学習の管理 | 間違って入力した学習を取り消せる | 設定で履歴を検索、1件削除、整理、全消去が可能 | 基本境界は実装済み。即時取り消しはP2 |
| 日付・数値入力支援 | 日付候補、数値・単位の入力支援 | 日付/時刻と数詞候補は実装。単位・桁確認ナビは未実装 | P2 |
| 表現モード・連想変換 | 話し言葉、方言、文語、類義語・言い換え | 未実装 | P2以降。まず通常文の精度を上げる |
| プライバシー/プロテクト | 学習抑制、会議中の推測候補抑制 | 手動プライベートモードとmacOS secure input連動は実装 | P1。会議検出より実アプリ検証を優先 |
| 専門辞書 | 分野別辞書や追加辞書を選択 | 基本辞書、3分野、外部辞書パック境界を実装 | 実装済み。品質・ライセンスgateを維持 |
| OS横断同期 | 学習・確定履歴・登録語を複数OSで同期 | 未実装。履歴は端末内のみ | P3。暗号化・競合・削除同期の設計が先 |
| 校正・辞典・生成AI | 不適切表現の指摘、辞典検索、文章書換え | 未実装 | 非目標。別製品機能として評価する |

## 現在のSlimeの課題

### P0: 変換品質

1. **学習前の左文脈に使う製品データがまだない。** 2回以上確認した端末内の前後ペアは、通常変換の順位に反映して再起動後も使う。v3辞書パックの静的ルールは、保持している直前確定表記の最大128文字の末尾を長い一致から検索し、既存候補を最大8件だけ前へ移動できる。非公開の注釈corpusから、通常候補内にある非先頭表記だけを、観測数・次点差・占有率の保守的なgateで決定的TSVへ変換する生成器も実装した。重複・held-out原文一致をhashで除き、語彙非出力の集計だけを残せる。一方、実ルールを持つ商用パックは複数held-outのgateをまだ通していない。最終held-outは`acc@1=0.530`に対して`acc@10=0.835`、外部domain devは`acc@1=0.6405`に対して`acc@10=0.9758`で、cold startで正解候補を先頭へ上げる汎用データは引き続き必要である。直前語の辞書品詞classへbackoffする軽量方式は未使用testを1件悪化させ、公開条件を確認した日本語4,100文を追加したword bigramも最終held-outを`0.530→0.525`へ悪化させたため採用しない。一般テキストを保守的な表層/読み列へ変換し、held-out一致と未知漢字を除外する中立な評価ツールは残す。
2. **正解が上位10件に入らない語彙・複合語が残る。** 人名、固有名詞、生産的複合語が中心。短い読みはN-best 32と2〜6要素の補助探索、長い読みは最良分割の各文節内だけを組み替える追加22件で回収範囲を広げた。外部文から自動生成した複合語診断では、信頼できる欠落2件に対して探索幅4→8・合成上限16→64は回収0で約5倍遅くなり、完全一致の外部辞書は回収2・回帰0だった。信頼済みの非公開注釈corpusから、既存の全bounded経路で生成欠落し、追加後に通常候補へ実際に入る単独語・2〜6要素複合語だけを決定的TSVへ抽出する生成器を実装した。core探索はboundedのまま維持し、低頻度語は正しい読みを持つ小さな別辞書へ分離する。自動注釈の読みは製品gateに使わない。
3. **学習の副作用を測る評価はまだ実入力母集団ではない。** 単発の選択が定着候補を上書きする問題を修正し、一般的な同音語を異なる左文脈で使う固定データを29件へ拡張した。現在は学習で直る16件、元から正しいまま保持する13件、回帰0件を同じ試験で測る。この拡張で、通常履歴のノイズ抑制条件を文脈アンカーにも流用し、「部屋」のような短い確定語を左文脈として保持できない問題を検出した。短い語は通常履歴へ保存せず、次の変換の文脈アンカーにだけ使うよう分離した。一般履歴では別候補を直近にしたまま、短語文脈による候補選択、確定、永続化、再読込を型付きC ABIとmacOS Swift bridgeの両方で回帰に固定した。残る課題は実入力由来の母集団へ拡張することである。
4. **ライブ変換と通常変換は品質契約が異なる。** 同期coreに加え、製品と同じ`immutable snapshot → worker scoring → generation-safe apply`を公開集合で再生する評価器を持つ。モデル1位と2位の確信差を要求し、短いliteral末尾の単漢字化、活用語尾の置換、暗黙の数字化を拒否する。促音直前の誤った境界は解除して`不逮捕特権`、`混声合唱`、`専門学校`を回収する。単純主題`は`の同音語は安定接頭辞margin 1000とworker限定4-path再評価で`競争→競走`、`感染→艦船`、`機構…評点→気候…氷点`を修復する。さらに、全文候補15件に右suffixを完全保存し、安定接頭辞だけを同じ文字数のまま最大2文字変更する候補がある場合は、停止後workerへ全文を渡す。差分はcost差1500以内の漢字同士に限り、適用時にも同じ条件を検証し、数字suffixは従来の専用経路へ残す。これにより`ラーメンには自身があるが→ラーメンには自信があるが`のような早期固定を修復する。通常cost gapは1000、10文字以上だけ1500、switch marginは0.2、暗黙数字修復だけ0.1、workerは9文字以上で15-bestとする。10文字以上の通常targetでは、モデルが辞書baseより0.5以上優勢な場合だけ文字数変更を許可し、`ないか→内科`のような長文のかな残りを回収する。small Q3、公開language pack、短い読み`lambda=0.2`、4文字以上`0.5`では、UD dev 331件で`0.4713→0.7039`（77改善）、未使用test 323件で`0.4737→0.7461`（88改善）、JWTD 400件で`0.2075→0.4175`（84改善）、AJIMEE 200件で`0.3200→0.6150`（59改善）となり、4集合すべてCore正解からの退行0だった。残存LIVE誤りの`Spaceの1位 / 候補移動 / 候補欠落`は、UD dev `50/48/0`、JWTD `24/83/126`、AJIMEE `18/27/32`である。macOSは180 ms停止後だけtaskを起動し、世代、読み、文脈、preedit、client range、候補集合の不一致を無作用で破棄する。モデル込み最大RSSが大きいため標準同梱にはせず、更新版の実InputMethodKit入力を残るgateとする。

### P0: 製品としての動作境界

1. **macOSの最新インストール版はTextEditの再確認が必要。** 2026-08-08に、インストール済みbundleと対象buildの全ファイル一致、入力ソース選択、物理A-Zイベントに加え、候補表示、選択移動、確定までを一回限りtokenで確認した。診断には入力文字や文書内容を記録していない。その後、外部のキャレット移動・クライアント切替で端末内左文脈を破棄するSwift境界と、index指定時に候補UIの選択行を再同期するCore境界を追加した。macOSのキー入力hot pathも毎回のJSON生成・解析をやめ、Windowsと同じ同期型付きaction C ABIへ移行した。短い直前語を使う学習は、このSwift bridgeで候補index選択、確定、再起動後の順位まで通した。さらに物理入力gateはprepare時のTextEdit process IDと前面processを照合し、CoreGraphicsのHID system source以外や別アプリのeventでは、文字、候補操作、再変換、privacy確認を完了できないようにした。TextEdit・再変換・privacy stateには2時間の期限を追加し、期限切れtokenを無効化する。privacy prepareがSwift側で必須の対象process IDを設定していなかった不具合も修正し、private/resumeは起動中TextEdit、secure-inputは前面または明示したhost processへ固定した。対象processはPIDに加えて起動時刻と実行ファイルのSHA-256へbindし、PID再利用やアプリ再起動後のcheckを拒否する。release verifier、VM lifecycle、TextEdit、privacy gateは同じartifact情報をcanonical JSONで返す。アダプター試験、bundle build、再インストール、manifest一致までは通したため、更新版でも同じgateを再実行する。物理操作による完走と画面上の置換範囲の目視確認が残る。
2. **Windowsはx64とARM64の署名前ライフサイクルを自動化した。** x64/x86 TSF、候補UI、設定、unsigned installerに加え、Windows 11 ARM64の使い捨てVM上でx64/x86エミュレーションによるclean install、不正updateのrollback、旧版update、新版後のdowngrade拒否、uninstall、ユーザーデータ保持をgate化した。release packagingはcleanなGit revisionだけを受け入れ、revisionをinstaller metadataとuninstall registryへ埋め込んで署名検証・consumer lifecycleまで照合する。さらにRust DLL、COM DLL、登録helper、設定実行ファイル、ARM64X forwarderのPE version metadataにも同じ40文字revisionと3要素の製品versionを埋め込み、release assemblyとverifierが一つでも異なる署名済みpayloadを拒否する境界を追加した。2026-08-08にはinstall後の両bitnessの設定実行ファイルを非対話で起動し、隔離したユーザーデータ領域で原子的保存、再読込、変更通知、後始末も確認した。実payloadとinstallerが署名release gateで拒否されること、署名policyのEKU・signer境界も確認した。native ARM64 runnerでRust C ABI、TSF、設定、登録helper、native testをbuild・実行し、x64/ARM64実装をARM64X forwarderから両方load probeするCIに、ARM64X/x86専用installerの生成とclean install、失敗rollback、update、downgrade拒否、uninstallを追加した。さらにrelease verifierと署名済みconsumer lifecycleをARM64Xの全8ファイルとx86の4ファイルへ一般化した。署名verifierはcode-signing EKUに加えてRSA 2048-bit以上を要求し、旧版updateは現行signerまたは明示的に承認した旧thumbprintだけを受け入れる。対話evidenceはartifact hashだけでなくuser SID、session ID、boot時刻へ固定し、download reputation、実入力、候補、Search、Narrator、設定反映を順番に要求する。自動lifecycleはsame-version再実行とdowngrade拒否後にもinstalled manifestとユーザーデータの不変を確認し、対話gateと同じarchitecture、version、revision、signer、installer hash、manifest hashをcanonical JSONで出力する。hardware-backed鍵custodyはartifactから証明できないため、商用側の署名監査logを別gateとする。2026-08-08に確認した公開workflowの直近実行は、更新されたSDKでaccessibility provider headerより前にCOM基底宣言がなくx64/x86 buildに失敗していた。現在の差分は必要な基底headerを先に読み込み、ローカルのx64/x86 cross syntax checkを通した。一方、この未push差分に対するremote workflowの成功証拠、実証明書による署名成功、Windows Search、Narrator、実行中TSFへの設定反映、各アプリ互換性は未検証である。
3. **配布・更新の外部gateが未達。** macOSのPKG内署名検査、同一version再実行の冪等性、旧版完全置換、旧PKGによるdowngrade防止、安全な削除、ユーザーデータ保持のscriptは実装した。release buildはcleanなGit revisionだけを受け入れてrevisionをbundleへ埋め込み、TextEditとprivate/secure-input gateは指定されたrelease PKGの署名・公証を再検証した上で、展開したpayloadとsystem installの全ファイルmanifestへbindする。一方、実Developer ID署名、公証、使い捨てVMとconsumer sessionでの実行証拠はまだない。Windowsも全PE・uninstaller・外側installerの署名と実機結果が必要である。追加辞書については、署名、pack ID allowlist、最低version、期待pack数を同時に検証し、語彙を出さずにpack全体のSHA-256だけを返す最終CLIまで実装した。空集合、一部欠落、余分なpack、65件以上も失敗するが、実鍵・実packでの商用CI証拠は別途必要である。

### P1: 入力効率と安全性

1. **入力ミス訂正の実入力評価がまだない。** 1文字過多、隣接キー、隣接2文字の入れ替え、母音1文字の欠落、促音子音1文字の欠落、6文字以上のローマ字入力における子音1文字の欠落を通常候補へ追加し、元の読みを必ず先頭に残して訂正を表示する境界は実装した。一般語の正例41件と既知語・短すぎる入力などの負例41件はrecall 41/41、不要訂正0/41、全入力p95 1.5 ms級、訂正候補最大3だった。外部fixtureを語彙非出力で集計し、7種類ごとの最低件数、欠落、不要訂正、p95、候補数を失敗条件にできる評価器も実装した。残る課題は、同意・匿名化・削除手順を持つ商用側の実入力fixtureへ広げることである。
2. **補完は履歴依存でcold startに弱い。** 長い定型句、確定直後の次語、一般的な省入力データはない。巨大クラウド辞書ではなく、小さな同梱データとユーザー履歴を分離して評価する。
3. **候補由来をmacOSとWindowsで表示できるようにした。** Coreは候補の確定値と、ユーザー辞書、履歴、訂正、補完、日付・時刻、数値、静的文脈の由来を別の型付きmetadataとして返す。訂正前の読みも補足fieldに分離し、候補表示用の説明が確定文字列へ混入しない。既存JSONとv1 C callbackは従来表示を維持し、v2 C callbackだけが確定値・従来表示・由来・補足を個別に公開するため、公開済みadapterを壊さない。macOS候補panelは説明を右側の小さな補助labelとして描画する。WindowsのTSF adapterもv2を使い、候補選択は従来どおりindexだけをCoreへ返したまま、desktop popupでは確定値と説明を分け、UILess/UI Automationでは結合した読み上げ名を公開する。一般辞書候補は説明を付けず、由来が誤選択防止に役立つ候補だけを識別する。Windowsの実機Narrator確認は引き続きrelease gateである。
4. **誤学習の即時取り消しがない。** 設定画面から1件削除できるが、確定直後に元へ戻す操作はない。
5. **候補recallは、辞書に要素語がない語と、既知要素だけでは意味を決められないphraseでまだ不足する。** 8文字以下は候補末尾でN-best 10件から32件へ再探索する。16文字以下は、1かな読みや辞書上かな表記だけの語を含む完全一致語を2〜6語組み合わせ、最大16件を追加する。9〜128文字は全長N-bestを増やさず、最良分割を固定して各文節内8候補をbounded beamで組み替え、最大22件を追加する。これらは初回候補の順位を変えない。要素語自体が辞書にない場合や、既知要素の無条件な組合せが候補ノイズになる場合は、公開coreの探索量を増やさず、信頼できる読み・表記を持つ別辞書で完全一致phraseを追加し、回収・回帰・top-1・latency・bytesを商用側のCIで固定する。

`just evaluate-recall PATH` は外部の`読み<TAB>期待表記`を初回候補、短い読みの拡張候補、複合補助探索、長文の固定文節候補、既知要素だけで構成できるphrase欠落、未知要素を含む生成欠落へ分類する。`missing`総数は後二者を両方含み、既存CIのgateを緩めない。外部辞書を重ねた場合は、基本辞書で欠落した項目の回収数、生成回帰、top-1改善・回帰・先頭表記の変化、初回候補生成p95、辞書総bytesも分ける。固有名詞や有償語彙の実データは公開treeへ置かず、商用側のTSVを一時入力して同じ分類を使う。商用CIでは`--details 0 --json --max-regressed 0 --max-top1-regressed 0`を指定し、別domainでは`--max-top1-changed 0`も要求する。読み・表記は保存せず、入力エラーにも語彙自体を埋め込まない。入力形式と判断基準は[Candidate recall evaluation](candidate-recall-evaluation.md)を参照する。

### P1: 性能とサイズ

1. **長文候補表示の性能回帰を継続監視する。** N-best bucketが満杯になった後も、明らかに残らない候補ごとに最大80状態を全走査していた。最大costをbucketに保持して走査前に棄却するよう修正し、2026-08-08のheld-out 200件、同一Releaseの3回中央値はp95 23.66 msから12.10 msへ短縮した。品質指標と全候補・costは不変で、20 ms予算を満たした。入力長別の候補生成時間と、候補UIまで含む実アプリtailは引き続き追う。
2. **ニューラルrerankerはローカルopt-inまで進んだが、標準同梱はまだNo-Go。** zenz-v3.2-xsmallは3つのdomainでtop-1とMRRを改善し、最初のSpaceだけを対象にするoptional runtimeを実装した。辞書候補だけを並べ替え、履歴・ユーザー辞書などを保護し、LIVEとprivate modeから分離している。辞書1位と次点のcost差が1000を超える項目は採点せず、JWTD/AJIMEEのtop-1とMinCER@1を全件採点と同じまま保って、採点p95を33.46→27.80 ms / 49.64→41.01 msへ短縮した。候補数16/32への拡張はoracle recallを増やす一方でtop-1改善が小さく、長文の生成・採点p95を大きく悪化させるため不採用とした。同じprocessの複数engineはmodel/backendを共有し、2つ目のattachはprobeで0.000 ms、最大RSSは単一engineと同じ94.2 MiBの範囲だった。設定画面用の一時engineはモデルを読まない。Apple M3の曖昧な短いwarm Spaceは約9.6–10.1 msだが、モデル約20 MiB、短い入力でも最大RSS約90–91 MB、初回Space約23–26 msである。厳密照合したheld-out長文caseは期待候補へ改善した一方、初回Space 32.9 ms、最大RSS 94.2 MBだった。ad-hoc署名bundleは約66 MiB、単独起動直後のRSSは約46.8 MiB。モデルの再配布条件、attribution、Developer ID署名bundleでのcold start/RSS、実InputMethodKit入力が未確認のため、通常buildと公式releaseには入れない。
3. **実アプリend-to-endの性能計測が薄い。** Rust単体とInputMethodKitのmarked-text更新を分け、候補UI表示までを同一条件で測る必要がある。

### P2: 操作・アクセシビリティ

1. 候補ウインドウの文字サイズ、外観、ページング、キーマップのカスタマイズが限定的。
2. macOS候補UIのVoiceOver、クリック、複数ディスプレイ、縦書き、secure field切替を体系的に検証していない。
3. 話し言葉、文語、方言、人名優先などの表現モードがない。
4. 数値+単位、郵便番号、住所、人名などの日常入力支援が薄い。

### P3: 同期・クラウド・付加機能

1. ユーザー辞書・学習履歴の端末間同期がない。
2. 新語配信、地域語彙、クラウド辞書がない。
3. 校正、連想変換、辞典、翻訳、生成AI文章支援がない。

これらは差分ではあるが、Slimeの中心価値ではない。入力内容を外部へ送らない既定、アカウント不要、ネットワーク不要を壊す機能は、コアIMEから切り離された明示的なオプションとしてのみ再検討する。

## 今回の実装: 学習強度

従来は履歴を `last_used` 優先で並べていたため、100回使った候補でも、別候補を1回選ぶと次回から後ろへ下がった。

新しい規則:

- 5回未満は一時的な選択、5回以上は定着した選択として扱う。
- 定着候補は一時候補より先にする。
- 同じ強度の候補どうしは、従来どおり直近使用を優先する。
- `history.tsv` の形式、上限500件、プライベートモード、ライブ変換のconfidence gateは変更しない。

これは外部製品の内部実装を再現するものではない。「一時的な表記が普段の表記を壊さない」という一般原則を、Slimeの既存データだけで説明可能に実装したものになる。

## 今回の実装: 適応的な候補再探索

初回候補は従来どおりN-best 10件を使う。8文字以下の読みでユーザーが候補の末尾を越えて進んだときだけ、一度だけN-best 32件で再探索する。長い読み、ライブ変換、補完、文節変換には適用しない。

`あさいり`では初回候補にない「浅煎り」を拡張後に取得できる。release benchmark 1,000反復では、同じ読みの初回候補が約0.676 ms/op、拡張候補が約3.460 ms/opだった。約2.8 msの追加コストを通常のキー入力から外し、深い候補を明示的に探す操作だけへ限定している。

同じ候補末尾操作で、完全一致の要素語を2〜6語組み合わせる補助探索も実行する。読みは16文字以下、各要素4件、追加候補16件、各位置・要素数の途中状態64件（API上限512件）に固定した。当初は各要素を最低2かなに制限していたため、1かな読みの語を途中に含む複合を生成できなかった。探索上限を変えずに1かな要素を許可し、converterと候補末尾操作の両方へ回帰を追加した。さらに、その部分読みに変換表記が一つもない辞書項目だけはかな表記のまま接続し、最終結果が全かなの経路を除外することで、助詞を含む混在複合を候補枠を消費せず回収する。かなのみの助詞を含む10文字fixtureでも、初回N-best 10件にはない混在候補が候補末尾操作後にCoreへ追加されることを固定した。

2026-08-08のReleaseでは、1かな要素を含む3語fixtureが約0.020 ms/opだった。実辞書の`あさいり`補助探索は約0.009 ms/opから約0.114 ms/opへ増えたが、早期棄却後のN-best 32探索約1.120 ms/opとの合計は約1.23 msである。いずれも明示的な候補末尾操作だけで実行し、5 ms予算内に収まる。N-best 64は25件の小標本でp95約700 msに達したため採用しない。

5要素対応後、各要素4候補の専用fixtureはRelease 5,000反復で約0.085 ms/opだった。上限4要素で結果を生成しない基準状態は約0.042 ms/opで、追加費用は約0.043 msである。既存2〜4要素の探索時間と状態・出力上限は変えず、通常候補の初回表示には適用しない。

6要素対応も読み16文字、各要素4候補、各位置・要素数64状態、出力16件を維持した。同一Release build・10,000反復では、既存5要素fixtureが変更前約0.0849 ms/op、変更後約0.0852 ms/op、新しい6要素fixtureが約0.1228 ms/opだった。追加層も候補末尾で明示的に追加候補を探す操作だけに使う。

かなのみの助詞を含む4要素fixtureは約0.0034 ms/opだった。実辞書の`あさいり`は約0.115 ms/opで、かな要素対応前とほぼ同じである。かな表記と変換表記の両方がある部分読みでは変換表記だけを使い、すべてかなの候補は追加しない。

拡張後の候補は、Core内で生成できるだけでなく、typed C ABIとSwift/AppKit bridgeを通して選択・preedit・確定まで一致する回帰で固定した。この確認で、候補をindex指定した際にpreeditだけを更新し、候補UI側の選択行が古いまま残る経路を検出した。選択手段にかかわらず`ShowCandidates`で現在indexを再通知し、Enterやplatform側Finalizeが画面と異なる候補を確定しないようにした。

## 今回の実装: 長文N-bestの早期棄却

各入力位置のN-best bucketは、品詞状態ごとの上限に加えて全体を探索幅の8倍までに制限する。従来はbucketが満杯でも、新しい候補ごとに重複、品詞状態数、全体最大costを最大80状態の線形走査で調べていた。bucketの最大costを更新時に保持し、それ以上のcostを持つ候補は走査前に棄却する。

- bucket内の挿入順、品詞状態ごとの上限、同costの扱い、beam幅は変更しない。
- 固定dev 400件の全候補表層とcostは変更前後で完全一致した。
- held-out 200件の`acc@1=0.530`、`acc@10=0.835`、MRR、MinCERも不変だった。
- 同一Releaseのheld-out 3回中央値はp50 3.19 ms、p95 12.10 ms、p99 16.74 ms、max 19.77 msだった。
- 中立な長文fixtureの候補窓は、同一build条件の複数回中央値で13.13 ms/opから7.73 ms/opへ約41%短縮した。

`--export-nbest`の各項目には`input_characters`と`candidate_generation_ms`を含め、入力長別のtailを製品コードへ計測分岐を入れずに集計できるようにした。

## 今回の実装: 保守的な入力ミス訂正

辞書完全一致、ユーザー辞書、完全一致履歴がどれもないローマ字入力だけを対象に、1文字多い入力、隣接キー置換、隣接する2文字の入れ替え、母音1文字の欠落、促音子音1文字の欠落、子音1文字の欠落を試す。母音は`a/i/u/e/o`だけ、促音は入力中に既にある対応子音の1回複製だけに制限する。子音補完は短語の誤訂正と既存経路の探索量を抑えるため、6〜24文字の入力で既存母音の直前へ1文字だけ挿入する。訂正後の読みが辞書に完全一致する場合だけ最大3候補を追加する。

- 先頭候補は必ず元の入力とし、自動選択・自動確定しない。
- 表示は「日本　（にほんに訂正）」のように訂正を明示する。確定文字列に説明は含めない。
- typed C ABIとSwift bridgeの回帰で、注記付き候補を選択してもpreeditと確定文書には「日本」のようなsurfaceだけが入ることを固定する。
- 訂正候補を選んだ場合は、誤った読みではなく訂正後の読みとして学習する。
- 通常候補の最初のSpace操作だけに適用し、ライブ変換、補完、再変換、読みのある入力には適用しない。
- 固定fixtureで正例41件と、既知語・短すぎる入力・訂正不能入力の負例41件を別々に検証する。7種類の各訂正操作は2件以上を必須にする。
- 複数の訂正が成立する場合は、重複削除、隣接2文字の入れ替え、促音子音1文字の補完、母音1文字の補完、子音1文字の補完、隣接キー置換、任意の1文字削除の順とする。同じ訂正読みは最大2表記までにして3枠の独占を防ぎ、残りを別の訂正読みに使う。各表記は辞書コストを使って最大3件へ絞る。
- 2026-08-08のRelease、100 warmup、10,000反復では、隣接キー訂正は0.139 ms/op、母音欠落訂正は0.200 ms/op、促音子音欠落訂正は0.474 ms/op、子音欠落訂正は0.571 ms/opだった。いずれもSpaceによる通常候補表示だけで実行し、20 ms予算内である。

## 今回の実装: 端末内の左文脈学習

通常候補を明示的に確定したとき、`直前の読み・表記・今回の読み・表記`の関係を端末内に保存する。同じ関係を2回確定した後だけ、その左文脈で通常の全体履歴より先に候補を置く。例えば「文章→漢字」と「気持ち→感じ」を別々学習でき、再起動後も反映される。

- 1回だけの選択は順位を変えない。
- 5回以上使った定着文脈は、直近2回だけの一時文脈より先にする。双方が定着した後は直近の選択を優先する。
- 通常候補と確定直後の補完で同じ文脈ストアを使い、再起動前だけ別順位になる二重状態を持たない。
- 読み3文字未満や表記1文字の短い語は通常の候補履歴へ保存しないが、明示確定した表記は次の変換の文脈アンカーにできる。かなのまま確定した文字、句読点、ASCII入力はアンカーにしない。
- 上限500件で、文章全体や未確定テキストは保存しない。
- private modeと学習停止中は読み書きしない。
- 通常履歴の1件削除・整理・全消去で関連する文脈履歴も削除する。
- 履歴の再読込ではセッション内の直前確定も破棄し、削除済みの文脈関係を次の確定で作り直さない。
- 選択範囲の再変換は文書の別位置でも実行できるため、再変換前の確定を左隣として学習しない。再変換後の確定は新しい文脈の起点にできる。
- 壊れた文脈履歴ファイルは上書きしない。
- ライブ変換のconfidence gateには使わない。
- macOSでは、input sourceのactivate、client変更、外部caret移動、context reset後に次の文字入力が始まるとき、caret直前の既存文書を最大128文字だけ一時文脈として渡す。文書全体を読まず、取得失敗時は空文脈にして以前の文脈を再利用しない。
- Windowsでも、TSFの同期read/write edit session内でclientとcaret位置を比較し、新しいcompositionの開始時だけcaret直前の最大256 UTF-16単位を取得する。C ABIの先で同じ128文字上限を適用し、取得・変換失敗時は空文脈にする。secure activationではselectionの文字列を取得しない。
- 既存文書の読みは不明なので、この一時文脈は署名済みv3 context ruleによる順位付けだけに使い、端末内の文脈学習へ保存しない。private modeとsecure inputではclientの文書文字列自体を取得しない。

## 次の実装順

1. 商用利用・再配布条件を台帳化した注釈corpusを固定splitし、`just prepare-private-dictionary-candidate`でprivateな語彙packとv3文脈packのunsigned候補を作る。語彙を揃えたbaselineとの文脈差、複数held-outのtop-1、MRR、p95、bytes、別process起動時間、RSSが非悪化になるまで署名対象にしない。署名済み実アプリの初回起動と`just evaluate-adaptation`の実入力由来データは引き続き別gateにする。
2. 同じpipeline内の`generate-term-dictionary`とrecall gateで生成欠落語の回収、回帰、top-1変化、p95、bytesを固定する。読みを自動推定した語はrelease gateへ混ぜず、生成物は`UNSIGNED`が外れて`verify-signed`を通るまで配布しない。
3. 商用側で同意・匿名化した実入力の正例・負例を`just evaluate-typos`へ渡し、内容を保存せず訂正recall、不要候補、編集種別、p95、候補数を固定する。
4. 再インストール済みの最新macOS buildをTextEditの物理キーgateへ通し、逐次入力、候補操作、再変換、private/secure inputを確認する。
5. macOSの署名・公証・clean install・update・uninstallを初回販売のrelease gateにする。Windowsは初回macOS版のblockerにせず、購入導線を無効にしたまま公開CIでx64とnative ARM64の未署名ライフサイクル試験を維持し、商用側の署名済みVM gateへ進む。Windows版を販売対象へ加える条件は、hardware-backedな公開信頼RSA証明書で全PEとinstallerを署名し、同一revisionのclean VMで実アプリ入力、Search、Narrator、設定反映、install/update/downgrade拒否/uninstall、download reputationの表示を完走することとする。秘密鍵と署名サービス設定は公開repositoryへ置かない。

初回商用版の固定方針とconsumer sessionの合格手順は、[商用配布境界](commercial-distribution-boundary.md) と [macOS consumer verification](macos-consumer-verification.md) を参照する。
