# 同梱ライブラリでの候補選択と学習確認 — 2026-09-09

検証用macOSアプリの同梱dylibと同梱モデルを直接ロードし、C APIを通じて候補選択、
確定、学習、再読込を確認した。すべて新しく作成した検証用データディレクトリで行った。

次の経路が通った。

- 初期の「しょうめい→証明」を候補メニューから「照明」に変更し、Enterで「照明」を確定。
- エンジンを破棄して再作成しても、モデル有効のまま「照明」が先頭になる。
- 別のPythonプロセスから同じ検証用履歴を読み込んでも「照明」が先頭になる。
- プライベートモードでは以前の学習を参照せず「証明」が先頭になる。別候補の確定後も履歴ファイルは変わらない。
- 学習だけ無効にすると以前の「照明」は使われるが、新しい選択は保存されない。
- 別候補を選んでからEscapeで取り消しても、確定済みの履歴は変わらない。

確認には表示文字列とは別の候補値を使い、選択後のpreeditと確定アクションも検証した。
非学習の各ケースでは、検証用ディレクトリ内のTSVファイルの内容を前後で比較した。

## 確認中に分かった制限

後続の[短い語の文脈学習](short-context-learning-2026-09-09.md)で、文脈付きの短い変換先を改善した。
以下はその変更前の確認結果であり、通常履歴の最小文字数は後続でも維持している。

最初の確認に使った「はし→箸」は、現在の全体的な履歴優先順位の保存条件を満たさない。
`is_useful_history` は読み3文字以上・表記2文字以上などを要求する。
このため保存を期待した最初のprobeのassertionは失敗した。候補確定そのものの失敗ではない。
最終probeではこの条件を満たす「しょうめい→照明」を用いた。
短い語の文脈学習は別の条件を持つため、この結果から短い語の学習全般が無効とは結論しない。
