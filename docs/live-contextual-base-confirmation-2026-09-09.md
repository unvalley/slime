# 文脈付き辞書1位を再確認するLIVE経路（2026-09-09）

入力途中に推論を重ねた場合の「銀行口座の解説」を修正するため、文脈付き辞書1位をモデル込みの順位付けで再確認する限定的な経路を採用した。毎文字推論する既存例で「銀行口座の開設」へ改善し、逐次入力200件と全文入力後の比較では既存の出力を維持した。

## 状態の切り分け

実バンドルで記録した途中表示「吟子」「銀高校」「銀行口座の介せ」をCoreで再適用し、それぞれを一つずつ除外して最終requestを追った。「銀高校」を除いた場合だけ、最終requestが短い「かいせつ」から全文へ戻った。これは記録した表記を使うCoreの反実仮想試験で、除外後のモデル順位をすべて再計算した試験ではない。

短いrequestでも左文脈「銀行口座の」は渡っており、辞書1位は「開設」だった。問題は、この文脈付き辞書順位の差1962が通常の採点省略上限を超え、変換済みの表示「解説」が残ることだった。

## 試験する条件

通常のcost gateを超えた場合に限り、以下の条件をすべて満たす対象を採点する。

- 左文脈があり、読みが4〜8文字。
- 安定接頭辞を開き直すrequestではない。
- 現在の対象と文脈付き辞書1位が異なり、双方が漢字2文字。
- 辞書1位と次点のcost差が2500以下。

さらに、従来のモデル重みと確信度条件を適用し、モデル込みの順位付けでも辞書1位が先頭になった場合だけ候補を渡す。この追加経路では、採点が拒否されたときに辞書順だけで自動反映しない。モデル順位は辞書costとモデル尤度の混合値であり、モデル単独の尤度が最大だったという主張ではない。Coreの適用検査も維持する。

## 検証結果

検証用バンドルのローマ字10例×推論頻度3条件では、毎文字推論する「銀行口座の解説」だけが「銀行口座の開設」へ変わった。他の最終LIVE表記と全件の明示変換は一致した。

全文入力後に一度評価する既存かな2,745件とローマ字200件では、第一候補、LIVE変更・回復記録、worker status集計、正解数が前後で一致した。このローマ字200件はかな集合の一部と同じ内容で、独立した追加200例ではない。

追加の逐次入力試験は、同じローマ字200件について毎文字遅延taskを作成・実行・適用する。変更前後のバンドルに同じSwift実行ファイルを入れ、別々の検証用プロフィールを使う。途中の意図しない確定と、Enterが表示どおり確定することも検査する。実時間debounceや物理キー・InputMethodKitの試験ではない。

根拠は`target/evaluation/live-model-prefix-state-20260909/`と`target/evaluation/live-contextual-base-confirm-20260909/`に保存している。検証用実行ファイルは採用版から分離している。

## 逐次入力200件の結果

変更前後ともLIVE108/200、明示変換110/200で、すべての最終LIVE表示と明示変換出力が一致した。両実行で、途中の意図しない確定はなく、Enterによる表示どおりの確定を確認した。`batch-before.json`、`batch-after.json`、`batch-comparison.json`に保存した。「銀行口座」はこの200件には含まれないため、10例×3条件の改善と分けて扱う。

## 実装の確認

追加条件は、採点前の読み長・文脈・文字種・cost差と、採点後に辞書1位を支持するかの二段階で検査する。拒否時に辞書順だけを反映するfallbackには進まない。読みの基準表層はCoreの読み取り専用APIから取得し、評価器専用の診断APIを製品ポリシーに流用しない。

FFIのニューラル機能を含む45テストが成功。新しい回帰テストは、途中の「銀高校」適用から短い「かいせつ」scopeを実際に作り、文脈なし・現在表記と同じ辞書1位・cost上限超過を拒否することを確認した。Clippyも成功した。採点処理をtaskのメソッドへ分け、既存の`chunks_exact_to_as_chunks`警告だけ例外指定した。

最終コードでQAアプリを再ビルドし、同梱dylib・Q4モデルを使う30パターンのSwiftプローブを再実行した。試験版と全記録が一致し、毎文字推論する「銀行口座の開設」を確認した。QAアプリのad-hoc署名検証も成功。利用中のIMEへのインストールとユーザー履歴の変更は行っていない。
