# 文脈のある短いLIVE対象の採点範囲（2026-09-09）

Q4のLIVEで、辞書候補のcost差だけを理由にモデル採点を省略する条件を限定的に緩和した。全2,545件でLIVE第一候補は1,571→1,574、改善3件・既存正解の悪化0件。不正解同士の表記変更も0件だった。明示変換の全出力は一致し、1,576正解を維持した。

## 原因と変更

`てんきがいいからせんたくしよう`の実際のworker対象は、左文脈`天気がいいから`と読み`せんたくしよう`。辞書候補のcostは`選択しよう=7462`、`洗濯しよう=8570`で、差1108が従来の採点上限1000を超えていた。直接モデルを採点すると「洗濯しよう」が勝つが、実際のworkerでは採点に到達していなかった。

10文字以上の対象に限っていた上限1500を、左文脈が空でなく、対象の読みが6文字以上の場合にも適用する。Unicode文字数を使う。上限を無制限にはせず、確信度、文字数変更、深い辞書候補への変更、安定接頭辞、世代番号の検査は維持した。明示変換にはこの緩和を使わない。

`家に早く変える→家に早く帰る`は別問題。モデルは「早く帰る」を高く評価するが、短い対象の表層文字数が変わるため拒否される。この変更には文字数制限の緩和を含めていない。

## QAバンドルと時間測定

更新した`target/macos/Slime.app`と保存した変更前アプリに同じSwiftプローブを組み込み、それぞれの同梱dylib・Q4モデルを使って上記3例を再現した。変更前は旧表記、変更後は改善表記になり、Enterが表示どおりの文字列を確定した。プローブ専用の履歴ディレクトリを使い、利用中のIMEと履歴は変更していない。QAアプリのad-hoc署名検証も成功した。

固定60件を前後交互に3回ずつ測定したworker時間の各回中央値は、p50が31.22→26.52 ms、p95が63.21→64.24 ms、最大値が118.78→123.59 ms。この小標本では完了task数は前後とも47で、採点対象が増えた入力に対する負荷全体を代表しない。速度改善は主張しない。物理キー、180 ms debounce、InputMethodKitを通した入力遅延も未測定。

ローマ字入力中の推論頻度を変える既存10例×3条件も、更新したQAバンドルで再実行した。30実行すべてで明示変換は旧版と一致し、途中の意図しない確定はなかった。毎文字推論する条件の「天気がいいから選択しよう」だけが「洗濯しよう」へ改善し、他の最終LIVE表記は一致した。これは実時間の非同期スケジューラ試験ではない。結果は`prefix-results.json`と`prefix-verification.json`に保存した。
