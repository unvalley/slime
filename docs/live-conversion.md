# ライブ変換

Slimeのライブ変換は、入力全文を毎回無条件に第一候補へ置き換える機能ではない。
未確定の末尾を毎キー評価し、後続入力でも維持された文節はmarked textに残したまま
変換対象から外して、変換対象を右へ進める。曖昧な範囲は読みのまま扱う。

## UXの契約

- 未確定ローマ字をかな漢字変換のラティスへ入れない。
- 未確定ローマ字から新しい信頼できる全文候補が作れない間だけ、かな読みが変わっていない範囲の変換結果を保持する。
- 新しい候補の差が閾値未満でも、上位経路のいずれかが直前の変換結果と新しいliteral suffixの連結に完全一致し、1位との差が同じ閾値内なら安定した拡張として採用する。
- 内容語だけでは固定しない。助詞まで含む信頼できる文節が、後続入力を加えたラティスでも維持された時点で固定する。
- 固定した文節はmarked textに残すが、以後のキーでは変換対象に含めない。
- 固定前の範囲が曖昧なら、古い変換と新しい末尾を機械的に連結せず、その範囲だけを読みへ戻す。
- Enterは、その時点で画面に表示されているmarked textと同じ文字列を確定する。
- Escapeで読みへ戻した後は、現在のcompositionが終わるまでライブ変換を再開しない。
- ライブ表示をEnterで確定しただけでは学習しない。Space後の候補選択や補完候補の選択は学習する。
- 5文字以上の読みに限り、Space後に選び直した表記を同じengine session内の次回入力から使う。永続履歴は同じ表記を2回以上選んだ場合だけ使う。どちらも上位10経路に残り、第一候補とのコスト差が2500以内の表記に限る。private modeと学習オフでは使わない。
- Spaceによる明示変換ではライブ変換の信頼度閾値を使わず、通常の候補一覧を提示する。

期待する遷移の例:

```text
確か → 確かn → 確かな
日本 → 日本g → 日本語
ライブ変換 → ライブ変換d → ライブ変換で
変換が → 変換がt → 変換がts → 変換がつ
変換がつ → 変換が続く → 変換が続くと → 変換が続くとお
今日は → 今日はいい
そう → そうs → そうしま → そうしましょう
```

## 状態と判定

`slime-core`はライブ候補、その候補が覆う完全なかな読み、変換対象から外した文節を
別々に保持する。`n`、`k`、`sh`
など次のかながまだ決まらず、新しい信頼できる候補も作れない間は、かな読みそのものが
変わっていない直前の表記へ未確定ローマ字だけを付けて表示する。母音の入力でかなが確定した
時点では固定前の範囲を再評価する。これにより入力途中の不要なrollbackを防ぎつつ、分割境界が
変わった際に`1勝ち + がう = 1勝ちがう`のような、ラティスに存在しない表記を作らない。

表示は次の範囲に分かれる。いずれもアプリへの確定ではなく、Enterまでは全体がmarked textである。

| 範囲 | 意味 |
| --- | --- |
| stable prefix | 助詞で閉じ、後続入力でも維持された文節。以後のキーでは変換しない。 |
| pending prefix | 一度は閉じたが、右側の入力が未完成で全文候補が境界をまたいだ文節。表記を保ったまま右側だけ読みで表示する。 |
| fallback prefix | 句読点や開き括弧までの表示。右側が曖昧になっても、ここより左は読みへ戻さない。 |
| target | まだ固定していない末尾。毎キーここだけを変換する。 |

候補が一度1位になっただけでは固定しない。たとえば`こうい`の`行為`は、次の`う`で
`こういう`へ変わり得るため変換対象に残す。`変換が続くと`は、後続の`お`を加えた
ラティスでも同じ表記が維持された時点で初めてstable prefixへ移り、以後は`お`以降だけを
変換する。

stable prefixの境界は表示上の境界であり、ラティスをそこで切ると接続コストも切れる。
そのため、境界をまたぐ長い語・カタカナ語・`できる`や`という`のような語彙化した
ひらがな表現が全文ラティスで境界を越える場合に限り、境界を開き直す。

全文1位と2位の差が閾値未満でも、全文1位が「直前に表示したsurface + 新しく確定した
literal suffix」と完全に一致する場合は採用する。たとえば`ライブ変換`へ`で`を加えた
全文1位が実際に`ライブ変換で`なら、2位の`ライブ返還で`が近くても読みへ戻さない。
一方、古いsurfaceを末尾へ機械的に連結することはなく、全文ラティスが同じ表記を確認
できない`1勝ちがう`は採用しない。

辞書候補は通常2経路だけ探索する。上位2経路が同じ表記なら、内部の分割差を
ユーザーに見える曖昧さと誤認しないよう4経路まで適応的に広げ、異なる表記同士を比較する。
第一候補と次の異なる表記のコスト差が500未満なら、上記の安定した拡張を除いて新しい全文候補は採用しない。

ユーザー辞書の完全一致は常に優先する。入力履歴は、一度だけの選択や暗黙確定された
誤変換を再表示しないよう、上記の契約どおり繰り返し選ばれた5文字以上の表記に限って使う。
それ以外の履歴は、Space後の変換候補と補完候補の順位付けにだけ使用する。

### 停止後の順位付け

`live_candidate_ranking_snapshot`は、入力中のengineを参照しない不変のsnapshotを返す。
workerはこれを使ってキー入力の経路外で候補を順位付けし、`apply_live_candidate_ranking`は
compositionの世代・読み・文脈が変わっていない場合だけ結果を表示へ反映する。
この仕組みは`slime-core`にあるが、FFIとプラットフォーム層はまだ呼び出していない。
そのため現在のアプリでは、毎キーの同期表示だけが働く。

## 既知の限界

現在の既定rankerは、単語コストと品詞接続コストだけを使う。左文脈や文の意味を
理解しないため、`制度/精度`、`漢字/感じ`、`箸/橋`のような同音異義語を
信頼度閾値だけで正しく選ぶことはできない。

文節を固定すると、表示済みの文字が書き換わる量は減るが、入力を止めた時点の表記が
全文1位と一致しない場合が残る。末尾の語を読みのまま残す例（`愛とゆうき`）や、固定した
境界のせいで右側が別の語になる例（`母がいたと気には`）がある。停止後の順位付けは
これを直すためのものだが、上記のとおりまだ接続していない。

`slime-live-transition-evaluate`で、文節固定の導入前後を同じ入力で比べた結果:

| 入力 | 最終一致率 | rollback文字 | かな戻り項目 | 1キーp95 | 1キーp99 |
| --- | --- | --- | --- | --- | --- |
| AJIMEE 200件・5,820キー | 0.355 → 0.340 | 9,017 → 2,848 | 177 → 64 | 1.8 → 3.3 ms | 2.8 → 7.5 ms |
| JWTD dev 400件・11,263キー | 0.2175 → 0.2200 | 15,494 → 5,694 | 378 → 139 | 1.1 → 2.7 ms | 1.9 → 6.7 ms |

長い未固定の読みでは、1キーあたり数回のN-best探索が読み全体に走る。最大値は
AJIMEEで39 ms、JWTD devで24 msであり、文節が長く固定されない文で発生する。

今後も、精度だけでなく次を評価する。

- 同じ範囲での表記の往復回数
- ライブ候補を訂正するためのSpace、候補移動、Backspaceの回数
- 暗黙確定が履歴へ与える影響

## 検証

```sh
cargo test -p slime-core live_
just test-macos
SLIME_BENCH_ITERATIONS=100 \
SLIME_BENCH_WARMUP_ITERATIONS=10 \
SLIME_BENCH_LIVE_LENGTHS=10,50,100 \
cargo bench -q -p slime-core --bench engine
just evaluate-live-transitions crates/slime-tools/testdata/live_romaji_prefix.json
```

`evaluate-live-transitions`は入力を1キーずつ再生し、表示済みの文字が後から書き換わった量
（rollback）、変換済みの表記が読みへ戻った回数、暗黙の数字の混入、最終表示の一致率、
1キーのlatencyを集計する。`crates/slime-tools/testdata`の3ファイルは原因調査用に手で作った
84例で、入力頻度を代表しない。AJIMEEやJWTD devの評価JSONもそのまま入力にできる。
