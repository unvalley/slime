# 未確定ローマ字によるLIVE境界保護の消費（2026-09-09）

ローマ字入力途中の単独`n`が、次の確定かなに対して残すべきLIVE境界保護を消費する問題を修正した。ローマ字200件は105→106正解、悪化0件。かな直接入力2,745件は評価記録が一致し、LIVE1,685正解・明示変換1,686正解を維持した。

## 原因

`ginkoukouza`の段階では「銀行口座」のような短い候補を直ちに文節として固定しないため、`deferred_fragile_reading`に読みを保持する。次の`n`をflush相当の仮読み「ん」として評価した際、`take_deferred_fragile_extension`がこの情報を`take()`で消費していた。

続く`o`で実際のかな「の」が確定したときには保護情報がなく、「銀行口座の」が文節固定の対象になった。かな直接入力ではこの仮の「ん」の段階がないため、同じ最終読みなのにworkerの評価範囲が異なっていた。

未確定ローマ字が残る間は保護情報を参照するだけにし、確定かなになった時点で従来どおり一度消費する。コピーや追加のモデル推論は導入していない。候補数、モデル、重み、採点条件は変更していない。

## 検証

- Core243テスト成功。新しい回帰テストでは`ginkoukouza → n → o`に沿って、保護情報が残ってから消費されることを検査する。完成した全文の候補requestも、かな直接入力と一致する。
- Core/FFIのClippy成功。従来の`chunks_exact_to_as_chunks`警告のみ例外指定。
- かな直接入力2,745件で、第一候補出力、LIVE変更・回復記録、worker status集計、正解数が変更前と一致。
- 同じコーパスの200件をローマ字経由で再実行し、「彼に使えて長く→彼に仕えて長く」が回復。変更はこの1件のみで、明示変換の全200出力も一致。

ローマ字200件はかな2,745件の一部と同じ内容で、合計2,945件の独立例とは扱わない。ローマ字は製品の表に基づく一種類の入力列であり、全綴りや実際の利用頻度を代表しない。残る「ところ→と頃」「天覧→展覧」の入力経路差は未解決。
