# 目的語の後の動詞・助動詞候補をLIVEへ接続する試作

2026-09-14。v2を採用版Gとして通常ソースと `target/macos/Slime.app` に反映した。前の採用版は [本文支持を要求するLIVE・Space協調](live-space-body-support-2026-09-13.md) のF。

[実際のワーカートレース](live-object-desire-trace-2026-09-14.md) で、`この商品をかいたい` の採点要求は `かいたい`、左文脈は `この商品を` だった。解体と買いたいの辞書コスト差2115が通常ゲート1000を超え、モデル採点が始まっていなかった。[辞書の品詞に基づく候補回収](live-object-morphology-2026-09-14.md) では、汎用の複数語コスト窓で落ちる飼いたいも回収できた。

今回の試作は、その限定的な候補回収を実際のLIVE要求に追加する。対象は漢字を含む安定接頭部が「を」で終わり、残りの読みが3〜8文字の要求。辞書の動詞連用形と助動詞を組み合わせ、既存候補と表記が重複する場合は追加しない。候補はスナップショット内でキャッシュする。汎用候補窓と通常の1000/2000ゲートは変更せず、この構造がある要求に最大3500の追加ゲートを試す。

新しい長さの変更は、同一のモデル採点から得た本文スコアと終端込みスコアがともに辞書先頭より2以上高く、かつ両方で候補集合の首位である場合に限り承認する。代替順位は混合係数0.8、最小差1.0を使用する。承認は候補とコストを含む要求全体に結び付け、既存の入力世代・候補順列・安定接頭部検証を通す。

候補を追加するため、通常ゲートでも候補集合が変わる。追加ゲートが既存の順位付けに及ぼす影響も結果比較で確認する必要がある。単語の回収成功だけを採用根拠にはしない。

成果物は `target/evaluation/live-object-auxiliary-integration-20260914/`。3クレートの変更前・試作ソース、テスト付きビルドと復元スクリプト、50件の診断例、事前に作成した別動詞・対照例30件、既存5745件の入力と採用版F結果のハッシュを保存した。試作のビルド後は通常ソースを必ず復元し、通常の評価実行ファイルもFとバイト一致することを確認する。

採用判断には、目的の表示が実際に直ること、対照例と広いコーパスでの損益、ネイティブアダプタ経由の再現、処理時間を確認する。モデルや辞書の学習データと独立した評価であるとは主張しない。

## 最初の接続結果と採点枠の制限

最初の接続版v1は診断50件でLIVEの正解が42件から46件になり、4改善・0悪化・その他の表示変更0だった。改善は商品・製品・靴の「解体→買いたい」と犬の「解体→飼いたい」。Spaceは42件のまま、全出力が同一。これは調査・調整に使った例を含む結果であり、未知入力の精度推定には使わない。結果と実行ファイルを成果物内の `v1/` に凍結した。

v2では、通常ゲートを通らず追加した動詞・助動詞ゲートだけで採点した要求について、後処理とフォールバックを含めた最終候補が品詞・両モデルスコアの承認を持つ場合にだけ返す。これにより、新しい採点枠が無関係な名詞候補への切り替えを許可しない。通常ゲート内での候補追加の影響は、引き続き評価対象である。


v2も診断50件の4改善・0悪化を維持した。事前作成の別動詞・対照例30件ではLIVEが26/30から28/30に改善し、悪化・その他の表示変更はなかった。「この問題をと期待→この問題を解きたい」「この水を組みたい→この水を汲みたい」が改善。Spaceの28/30と全出力は同一だった。

残る「この服を期待」は安定接頭部がなく、要求全体が `このふくをきたい` であるため今回の限定した構造には入らない。もう1例の「この髪を切りたい」は期待表記を「紙」としたが、左文脈なしでは髪も自然であり、意味が一意に定まらない。結果を見て期待表記を変えず、両版で同じ出力として記録した。


## 広い入力での比較

v2と採用版Fの既存5745件を比較した。LIVEは3209/5745から3210/5745で、1改善・0悪化・その他の変更0。Spaceは3203/5745のまま全出力が同一。唯一の改善はMozc回帰テストの「この商品を買いたい」で、診断50件と同じ入力である。別の改善例として二重計上しない。

Fの評価時に固定していた別400件は、LIVE191/400、Space193/400で両版の全出力が同一だった。この400件は既存5745件と読みが重ならないよう選んだ集合だが、JWTDの学習側データからの抽出であり、モデル学習との独立性は保証しない。

診断50件、事前作成30件、広い比較で変更した入力を重複除去すると、ネイティブ検証対象は79件になった。今回確認した異なる改善入力は6件である。ネイティブアダプタと処理時間は検証中。


## macOSアダプタの再生結果

79件を履歴無効の隔離プロファイルで比較し、全文入力後の採点はLIVE6改善・0悪化・その他の変更0、1文字ごとの採点は7改善・0悪化・その他の変更0だった。両方ともSpaceの全出力を維持し、Space→Enterの確定一致をSwiftプローブ内で検証した。入力、モデル、FFI、ヘッダー、Swiftソースのハッシュを確認済み。

1文字ごとの再生では「この服を期待→この服を着たい」も改善した。全文入力後にだけ採点する経路では未改善のままであり、結果を混同しない。オフラインで改善した6入力に加え、逐次入力だけで改善した1入力を確認した。物理キー入力やInputMethodKitの画面描画までを測った結果ではない。


### 残るLIVEからSpaceへの不一致

商品・製品・靴の「買いたい」と犬の「飼いたい」は、LIVE表示とEnter直接確定では改善したが、Spaceを押すと両版とも「解体」になる。Spaceの全出力が不変という結果は、この誤変換が直ったことを意味しない。今回の変更によるSpaceの新しい誤変換はないが、正しいLIVE表示から誤ったSpace候補へ戻る操作上の不一致が残る。

既存の `apply_explicit_live_agreement` は漢字以外の文字列が同一の場合だけLIVEとSpaceを協調させるため、「解体」と「買いたい・飼いたい」の間には適用されない。この制約を一般に緩めるのではなく、辞書の品詞と本文・終端込みスコアで承認された今回のLIVE候補の根拠をSpaceへ渡せるかが次の検討課題になる。

79件のEnter直接確定も両入力順で検証し、確定文字列はLIVE表示と一致した。Spaceを後で押す再生のLIVE表示とも一致した。
