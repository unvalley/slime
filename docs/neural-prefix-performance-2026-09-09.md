# モデル候補の共通部分を共有 — 2026-09-09

## 変更

GPUが利用できる場合、候補をトークンの接頭辞木にまとめ、同じ文頭を一度だけ計算する。
分岐後は候補ごとのsequence IDを維持し、異なる履歴を混ぜない。各ノードの対数正規化項も
再利用する。空候補、他候補の接頭辞で終わる候補、重複候補、16件を超える複数バッチを扱う。

モデル、重み、候補集合、採用マージンは変更していない。キャッシュを常駐させる変更ではなく、
接頭辞木はその処理中だけ保持する。最大16個のsequence IDをu16のビット集合で表す。

初期試作は従来のサイズ上限を越える入力まで処理できてしまい、AJIMEEの1件で不要な
変換を表示した。最終版は共有前のトークン数で従来の上限を守る。

CPUの量子化カーネルではバッチ形状の変更で対数確率が最大0.357変わったため、CPUのみの
実行およびGPU非対応の環境では、従来と同じ独立した候補の並びを維持する。35候補・複数
バッチのCPU比較では、小数6桁で従来スコアと一致した。

## 品質と数値差

前段の[長文Space変換改善](explicit-ranking-2026-09-09.md)を基準に、実際のC APIを通して
比較した。全1,254項目でSpaceの先頭候補とLIVEの変更記録が一致し、処理ステータスの
内訳も一致した。

| 集合 | Space正解数 | LIVE正解数 |
| --- | ---: | ---: |
| JWTD 400 | 178のまま | 198のまま |
| UD dev 331 | 279のまま | 277のまま |
| UD test 323 | 271のまま | 276のまま |
| AJIMEE 200 | 138のまま | 147のまま |

GPUでは計算のまとめ方による丸め差があり、確率のビット単位一致は主張しない。
4種類の生スコア比較で最大約0.0099の対数確率差があった。記録された失敗例では、
Space候補一覧の下位順序がJWTDの3件、worker内の下位順序がJWTDの4件とAJIMEEの2件で
変わったが、そこでの正解候補の順位は変化しなかった。全候補の順序が完全一致する変更ではない。

## 処理時間

Apple M3で、JWTD・AJIMEE・UD devから各20項目、計60項目を使い、ビルドや別のモデル実行が
終了してから前後を交互に3回測定した。C APIのSpace処理時間で、画面描画は含まない。

| 指標（各回の中央値） | 前 | 後 |
| --- | ---: | ---: |
| p50 | 35.04ms | 34.86ms |
| p95 | 177.56ms | 162.10ms |

p95中央値は約9%短縮した。前のp95は175.17〜184.00ms、後は160.52〜178.78msで、
最終回だけは後の方が遅かった。常に速くなる保証や、最大遅延が改善したという主張はしない。
最初の試作測定はコンパイルと重なって遅く見えたため、採否にはその数値を使わなかった。

## 検証

neural有効のライブラリ試験12件とClippyを通過。分岐・同一候補・接頭辞候補・空候補・
16個すべてのsequence bit・CPU向け独立配置を検証した。C ABI smokeとSwiftアダプターも通過。

`target/evaluation/neural-prefix-20260909/`に開始時ソース、単独差分、比較実行物、
生スコア、全件結果、反復測定を保存。`evaluator-after`は初期試作、`evaluator-final`が
CPUと処理対象上限を維持する採用版である。過去のローカルアプリは`Slime-before.app`へ保存した。
最終アプリではモデルのSHA-256と設定を確認し、更新した同梱ライブラリを使うSwift検証と
署名検査を通過した。`final-sha256.txt`にソース・実行物・アプリのハッシュを記録した。

画面ロックを検出したため、入力ソースの切り替え、インストール済みIMEの差し替え、
実キーでのTextEdit検証は行っていない。ローカル検証用アプリと、実入力・配布の検証は別の段階である。
