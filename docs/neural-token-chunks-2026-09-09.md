# トークン容量に応じた候補分割（2026-09-09）

モデル採点時、固定の候補件数でまとめるだけでなく、前文脈と候補のトークン合計が容量に収まるように分割する。従来の件数で収まる場合は同じ分割を維持する。各候補の順序は変えず、単一候補自体が容量を超える場合はエラーを維持する。

32候補実験で採点に失敗したAJIMEE1429は、変更後に全候補を採点でき、「ボールを奪取」が首位になった。従来はトークン上限エラーにより採点を放棄し、辞書先頭の「ダッシュ」が残っていた。以前から成功していた5つの診断用候補集合では、スコア出力が小数6桁精度で一致した。

## 現行設定での検証

候補数は採用済みの設定を維持し、1,654問を現在のソースから再ビルドした評価器で再実行した。

- 明示変換は全問の出力が変更前と一致。
- LIVEの正解数は全6集合で同一。
- AJIMEEのLIVE処理成功が162→164、no-change statusが38→36。従来採点できなかった長い入力を処理できるようになった。
- LIVEの変更記録はAJIMEE1236の1件だけ増えた。かなの多い未解決表示から漢字を含む表示へ変わったが、「便指揮」「法廷」など誤変換が残り、両者とも完全一致ではない。この変化を「全出力が同一」とは扱わない。

容量境界・候補の保持・通常分割の維持を確認するテストを追加し、neuralテスト10件成功。Clippyも通過した（既存の別ファイルのchunks_exact警告は除外）。QAアプリをモデル同梱で再ビルドし、署名検証とSwift経由の代表例2件を確認した。これはローカルad-hoc署名アプリであり、インストール・公証・実機キー入力の検証はしていない。

## 再現資料

`target/evaluation/token-chunks-20260909/` に変更前ソース、`implementation.patch`、単体テスト・ビルドログ、6つの候補集合の採点結果、全評価JSON、`run-integrated.py`、`analyze-integrated.py`、`integrated-comparison.json` を保存した。旧QAアプリは `Slime-before.app` に保存。

容量超過した入力では追加のdecodeが必要になるため、従来の採点失敗より処理量が増える。この変更は候補数32の採用とは別であり、32候補で生じた他の順位悪化は解決していない。
