# ローマ字経由のLIVE評価差（2026-09-09）

現在のQ4 QA設定で同じ200件を入力すると、かな直接入力はLIVE108正解、ローマ字経由は105正解だった。明示変換は両方110正解で、全200件の第一候補が一致した。これは入力経路の比較であり、この段階で製品設定を変更して悪化させた結果ではない。

## 銀行口座の例

`ぎんこうこうざのかいせつ`を直接入力すると、最終workerの対象は全文になり、候補は「銀行口座の解説」cost11833、「銀行口座の開設」12780など。モデルが「開設」を選べる。

`ginkoukouzanokaisetsu`を入力すると、途中のモデル適用なしでも最終workerは左文脈「銀行口座の」、対象「かいせつ」に分かれる。この文脈付き候補では「開設」cost1844が1位、「解説」3806が次点だが、差1962が採点上限を超えて採点されない。4文字なので短い対象の辞書base反映経路にも入らず、表示は「銀行口座の解説」のまま残る。

両経路の確定済み読みは同じ。`requests.json`にCoreの実際のscopeと候補を保存した。モデルを何度も適用することだけが原因ではなく、通常のローマ字入力途中の状態遷移だけで評価範囲に差が生じる。

## 200件の対照試験

前段の文字数変更確認で使った追加200件を、製品のローマ字表から入力列へ変換した。長いかな列を優先し、複数の綴りがある場合は表の先頭の綴り、`ん`は`n'`を使う。対応しない記号などはそのまま入力した。代表的な一種類の入力列であり、すべてのローマ字綴りや利用者の入力頻度を代表しない。

全200件をLIVE無効の実際のSlimeEngineで入力し、かな直接入力との読み表示一致と途中の意図しない確定がないことを検査した。評価には現在のニューラル実行ファイルを使い、途中のモデル推論は行わず、全文入力後に一度だけ遅延taskを実行した。

| 指標 | かな直接 | ローマ字経由 |
| --- | ---: | ---: |
| LIVE完全一致 | 108/200 | 105/200 |
| 明示変換完全一致 | 110/200 | 110/200 |

LIVEは5件の表記が変わり、正解から不正解への変化3件、不正解同士の変化2件、改善0件だった。

- 「彼に仕えて長く」→「彼に使えて長く」
- 「…しまうところが玉に瑕」→「…しまうと頃が玉に瑕」
- 「孝明天皇の天覧に供せられた」→「孝明天皇の展覧に供せられた」
- 不正解同士の変化では「他ののうち→他の農地」などの部分改善と、「感ず→間ず」などが混在する。全文正解とは扱わない。

## 次の修正対象

かな直接入力の完全一致数だけでは、実際のローマ字経由のLIVE品質を代用できない。以降の文節固定・scope変更では両入力経路を対照評価する必要がある。

Coreは未確定ローマ字をflush相当で評価するため、例えば単独`n`が一時的に`ん`として候補計算へ入る。これが安定接頭辞や途中表示の保持に影響している可能性があるが、5件すべての根本原因としてはまだ確認していない。まずこの状態遷移を追い、採点上限の緩和だけで症状を隠さずに修正する。

製品コードとQAアプリはこの調査では変更していない。生成スクリプト、入力、Core round-trip検証、実際のrequest、モデル出力、差分、ハッシュは`target/evaluation/live-prefix-scope-20260909/`に保存した。物理キー・InputMethodKit・実時間debounceを通す試験は別途必要。

### 追加の状態追跡

各キーのCore表示とrequestを`trace.json`に保存した。「銀行口座の」までは両経路が全文scopeで一致し、その次の`か`が解決した時点でローマ字側だけsuffix scopeになる。`n`だけが原因だとはまだ断定できない。
